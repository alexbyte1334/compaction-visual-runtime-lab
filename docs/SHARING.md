# 15 分钟组会走查

## 0–2 分钟：我想解决的具体问题

“我做了一个小实验：排查 refresh token 故障时，源码和测试输出占满了上下文。删掉最早的消息可以省 Token，但下一步还记得约束吗？我用同一份输入比较了三种处理方法。”

明确说明这是合成学习案例。打开故障源码，展示 refresh endpoint 错把 expected_kind 写成 access；真实测试会出现 refresh 不被接受、access 不应被接受却通过这两处错误。

## 2–6 分钟：逐步展开 Runtime

点“创建实验”，然后点“下一阶段”。第一次只创建快照，不调用压缩器。解释增长图的数据来自采集结果，预算是本地 JSON 的 tokenizer 计数。

打开 policy_request：哪些必须保留，历史还能占多少，工具是否配对。打开 selection：当前规则为什么 KEEP 约束、COMPRESS 长测试输出、DROP 重复诊断摘要。

不要说“这是模型内心如何思考”。现在没有模型参与；将来接模型也只能展示返回的决策字段。

## 6–9 分钟：任务真的继续了吗

打开 Before/After 和 validation，展示引用原文、状态保留与预算检查。只有 Commit 成功，才点“恢复任务并运行测试”。展示真实 diff 和 83 passed。

解释恢复 Worker 的局限：它是固定规则程序，先核对合同和文件一致性，再做已知小修复；这个实验证明 Runtime 交接可用，不证明模型压缩普遍可靠。

## 9–12 分钟：对照与失败比成功更有价值

运行三组对照。完整上下文能修复但超过压缩目标；截断很小但丢失合同，Worker 拒绝行动；结构化压缩同时保留合同并通过测试。

重置为“伪造压缩证据”，展示候选虽然生成了，但 source quote 不匹配，Runtime 不提交。再看“丢失早期约束”，恢复按钮禁用。说明省 Token 不值得牺牲任务约束。

## 12–15 分钟：机制结论与下一步

“我的实验把三件事拆开了：Provider 产生候选，Runtime 验证并决定是否提交，Worker 用实际测试证明能否继续。压缩结果不是产生出来就可信。”

展示后续待办：接真实模型、保存真实回放、多案例重复评测、多轮压缩。官方 compact 的压缩项不可人工解释；本实验解释的是我们自己的工程机制。

可能被问：

- **为什么不用字符串摘要？** 可以加入简单摘要基线，但也必须用同样的恢复合同和任务测试检验。
- **Token 减少 70% 就算成功吗？** 不算，缺失约束或无法通过回归测试都失败；以当次实测为准。
- **为什么测试那么多？** 3 个行为回归 + 80 个合成诊断样本，用真实测试输出制造上下文增长；不是 83 个不同业务场景。
- **这是不是已经做完 Agent？** 没有，现在是最小 Runtime 实验和脚本 Worker，模型智能与生产恢复能力仍待验证。
